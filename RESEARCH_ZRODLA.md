--- SUMMARY ---
Hermes Agent (Nous Research, open source MIT, Python) to samodoskonalący się agent AI instalowany na własnym serwerze (VPS/desktop). Rdzeń = jeden proces AIAgent (run_agent) + długo działający Messaging Gateway z 25+ adapterami platform (Telegram, Discord, Slack, WhatsApp, e-mail itd.), sesje w SQLite (~/.hermes/state.db, FTS5), pamięć jako pliki markdown (MEMORY.md/USER.md) + wtyczki pamięci (m.in. Honcho), skille jako katalogi z SKILL.md, MCP (stdio i HTTP), sub-agenci przez delegate_task. Własną aplikację czatu podpina się przez: (a) OpenAI-kompatybilny API server (HTTP+SSE, Bearer key), (b) TUI Gateway JSON-RPC po stdio LUB WebSocket, (c) ACP, (d) webhooki HTTP z HMAC, (e) własny adapter platformy. Multi-user: jeden gateway obsługuje wielu użytkowników z sesją per użytkownik (allowlisty + parowanie DM), ale pamięć i dysk są wspólne w ramach profilu; twardą izolację (prezes vs dyrektorzy) dają PROFILE — wiele niezależnych agentów na jednym VPS (osobne configi, klucze, pamięć, boty), opcjonalnie zmultipleksowane w jeden proces. Modele: Nous Portal (OAuth, 300+ modeli), Anthropic, OpenAI, OpenRouter, Gemini, Bedrock, Azure, Ollama/vLLM/LM Studio i custom endpoint; klucze w ~/.hermes/.env. Uwaga: oficjalna domena to hermes-agent.nousresearch.com — strona hermes-agent.ai to serwis firm trzecich.

2) API DLA WŁASNYCH KLIENTÓW. Tak, da się podpiąć własną aplikację czatu, oficjalnie na 4 sposoby: (a) OpenAI-kompatybilny API server — HTTP + SSE na porcie 8642; włączasz API_SERVER_ENABLED=true i API_SERVER_KEY w ~/.hermes/.env; autoryzacja: Authorization: Bearer <klucz>; endpointy /v1/chat/completions (streaming SSE), /v1/responses (stanowe konwersacje: previous_response_id albo nazwane 'conversation'), /v1/runs (start/status/eventy/approval/stop), /v1/models, /api/model/options, /health; nagłówki X-Hermes-Session-Id / X-Hermes-Session-Key wiążą żądania z sesją. Każdy frontend mówiący formatem OpenAI (Open WebUI, LobeChat itd.) działa od ręki — to najprostsza droga dla własnej apki. (b) TUI Gateway JSON-RPC — po stdio LUB WebSocket; pełna kontrola: prompt.submit, session.create/steer/branch/history, approval.respond, clarify.respond, config.set, streaming eventów (message.delta, tool.start, approval.request...) — do budowy własnego pełnego hosta czatu. (c) ACP (JSON-RPC stdio) dla IDE. (d) Webhook adapter (port 8644, HMAC, trasy z szablonami promptów i deliver na dowolny kanał) do wyzwalania agenta zdarzeniami. Alternatywnie można napisać własny adapter platformy (adapter.py + plugin.yaml) i mieć swoją apkę jako pełnoprawny 'kanał'.

## 1) Jak działa szablon one-click "Hermes Agent" i "Hermes Workspace"

- **Hermes Workspace** (hostinger.com/applications/hermes-workspace) - paczka DWÓCH kontenerów: gateway agenta (`nousresearch/hermes-agent`, port 8642) + webowe UI (`ghcr.io/outsourc-e/hermes-workspace`, port 3000) z chatem, pamięcią, marketplace skilli, terminalem w przeglądarce i orkiestratorem multi-agent "Conductor". - **Hermes WebUI** (hostinger.com/applications/hermes-webui) - samo UI chatu (projekt hermes-webui), wymaga aktualizowania razem z agentem (pinuj obie wersje).

Kroki po instalacji (Agent): pierwszy start CLI odpala kreator - (1) tryb: **Full setup** (Quick Setup = logowanie przez Nous Portal bez kluczy), (2) provider modeli - przy kredytach nexos.ai wybierz "Nexos.ai AI gateway" (klucz już wypełniony), (3) kanały komunikacji (Telegram/WhatsApp itp.), (4) narzędzia - przy kredytach Oxylabs zaznacz Web Search & Scraping z providerem Oxylabs. ## 3) Bezpieczeństwo produkcyjne

- **Firewall:** gateway wykonuje tylko połączenia wychodzące - nie potrzebuje ruchu przychodzącego. Zamknij porty: `sudo ufw deny 8642` i `sudo ufw deny 9119`. Dostęp do UI przez tunel SSH, Tailscale albo reverse proxy - nie wystawiaj portów gołych na świat. Hostinger dokłada firewall panelowy i ochronę DDoS. Dodatkowo: wyłącz login root po SSH, fail2ban, skaner malware.
- **Sandbox i allowlista:** domyślnie agent wykonuje komendy BEZPOŚREDNIO na serwerze - przełącz na `hermes config set terminal.backend docker`. Dla botów (Telegram itp.) ustaw `allowed_user_ids` w config.yaml, inaczej każdy, kto znajdzie bota, może nim sterować.
- **Domena + SSL:** Hermes nie ma wbudowanego TLS. Produkcyjnie: reverse proxy (Nginx/Caddy/Traefik) z certyfikatem na domenie, a w Workspace ustaw `COOKIE_SECURE=1` + `TRUST_PROXY=1`; przy bindowaniu na 0.0.0.0 wymagane `HERMES_PASSWORD`, zalecany `API_SERVER_KEY`. 1) BEZPIECZEŃSTWO WYSTAWIENIA AGENTA Z SHELLEM NA ZEWNĄTRZ

(a) Koszty tokenów: soft darmowy (MIT), płacisz za tokeny + hosting; rój subagentów (delegate_task) = każdy subagent to osobne wywołania LLM; kontrola kosztów = tanie modele do subtasków (DeepSeek V4 ~$0.14/$0.28 za mln tokenów), drogi model tylko do orkiestracji; koszty rosną od długich rozmów, dużych wyjść narzędzi (scraping stron!), retrajów i równoległości — dla klienta zewnętrznego konieczny twardy budżet/limit per zadanie i monitoring. (b) Stabilność/aktualizacje: projekt bardzo młody i szybki (v0.2 w lutym-marcu → v0.9 w maju 2026), 3 CVE w Hermesie opisane przez CSA w jednym miesiącu, webui wersjonowane osobno — potrzebny stały proces: śledzenie releases/security advisories, staging przed produkcją, plan rollbacku. (c) Zależność od Nous Research: bundlowane narzędzia (search/extract/browser/vision/TTS) i OAuth dashboardu idą przez Nous Portal — awaria/zmiana cennika Portalu uderza w produkt; mitygacja: własne klucze API do modeli i niezależne narzędzia (własny search API), self-hosted OIDC zamiast OAuth Nous. (d) Ryzyko architektoniczne (CSA): trwała pamięć + szerokie narzędzia + wykonywanie sterowane promptem to powierzchnia ataku, której nie widzi tradycyjny monitoring — dla klienta zewnętrznego trzeba założyć monitoring warstwy promptów i regularne audyty, nie tylko patche.
